## 二、招标文件的骨架：标准章节框架

经过对 15 个文件的逐章梳理，招标文件的核心框架高度一致。建议 rfp 模块以此为基础建立模板体系：

### 2.1 通用骨架（适用于货物/服务/工程三类）

```
第一章  招标公告（或投标邀请书）
第二章  投标人须知
        2.1 投标人须知前附表（关键表格）
        2.2 总则
        2.3 招标文件
        2.4 投标文件
        2.5 投标
        2.6 开标
        2.7 评标
        2.8 合同授予
第三章  评标办法
        3.1 评标办法前附表
        3.2 评审标准
        3.3 评审程序
第四章  合同条款及格式
第五章  采购需求（或技术规格、工程量清单）
第六章  投标文件格式
```

### 2.2 三类采购的差异化要点

| 章节 | 货物类 | 服务类 | 工程类 |
|------|--------|--------|--------|
| 采购需求 | 技术参数表 | 服务内容与考核指标 | 工程量清单 + 图纸 |
| 评标办法 | 侧重价格分（30-50%） | 侧重技术方案（40-60%） | 综合评估 |
| 合同模板 | 供货合同 | 服务合同 | 施工合同（含质保金条款） |
| 资质要求 | 生产许可/授权 | 服务资质/业绩 | 建筑业资质/安全生产许可 |

### 2.3 "投标人须知前附表"是关键中的关键

这个表格是整本招标文件的"操作索引"，建议 rfp 模块把它作为核心数据结构。包含字段：项目名称、采购编号、采购人信息、采购代理机构、最高限价、投标有效期、投标保证金、履约保证金、投标文件递交截止时间、开标时间地点、评标委员会组成等。

## 三、法律法规合规：不可逾越的红线

招标文件本质上是法律文书，下面的法规清单是编写招标文件的"必查清单"：

### 3.1 核心法律框架

| 层级 | 法规名称 | 适用范围 |
|------|----------|----------|
| 法律 | 《中华人民共和国招标投标法》 | 工程建设项目 |
| 法律 | 《中华人民共和国政府采购法》 | 政府采购项目 |
| 行政法规 | 《招标投标法实施条例》 | 招投标活动细则 |
| 行政法规 | 《政府采购法实施条例》 | 政府采购细则 |
| 部门规章 | 《必须招标的工程项目规定》（发改委16号令） | 强制招标门槛 |
| 部门规章 | 《政府采购货物和服务招标投标管理办法》（财政部87号令） | 政府采购招标程序 |
| 部门规章 | 《政府采购非招标采购方式管理办法》（财政部74号令） | 竞争性谈判/磋商/询价 |

### 3.2 合规红线（投标人最容易挑刺的点，rpq 模块应内置检查）

1. **资格条件不得排斥潜在投标人**：不得以不合理的条件限制或者排斥潜在投标人（《招标投标法》第18条）。资质要求必须有法律或项目实际需要依据，不能拍脑袋写。
2. **评审标准必须量化**：评标办法中的打分项必须可量化、可验证，禁止使用"优/良/中/差"等模糊标准（财政部87号令第55条）。
3. **合同条款必须与招标文件一致**：《招标投标法》第46条规定，招标人和中标人不得再行订立背离合同实质性内容的其他协议。所以合同模板必须完整写入招标文件。
4. **等标期要求**：招标文件发售到投标截止不得少于 20 日（工程类）或按财政部门规定。
5. **中小企业政策**：政府采购项目必须落实中小企业预留份额和价格扣除（财库〔2020〕46号）。
6. **禁止地域限制**：不得限定供应商所在地、所有制形式、组织形式（财库〔2019〕38号）。

### 3.3 建议 rfp 模块内置的合规检查项

- 资格条件扫描：是否有不合理的注册资本、资产总额、营业收入、特定行政区域业绩等限制
- 评审办法检查：分值是否相加等于 100、是否包含不可量化项
- 时间节点计算：等标期、答疑期、公示期是否合规
- 政策条款引用：是否遗漏中小企业声明函格式、是否遗漏节能环保产品清单

## 四、Markdown 源码 + 渲染引擎方案

### 4.1 推荐架构

```
.yaml 模板定义文件（章节结构、变量占位符）
    │
    ├── 渲染引擎 ──→ .md 源文件（Git 友好、可 diff）
    │                    │
    │                    ├── Pandoc + Lua filter ──→ .docx（标准公文格式）
    │                    └── WeasyPrint / Typst ──→ .pdf（排版精细）
```

### 4.2 关键设计原则

- **模板与内容分离**：模板定义章节骨架和法律条款（每个甲方都需要相同的法律文本），内容填充具体项目信息
- **扩展 Markdown 语法**：内嵌 `:::` 语法块处理"投标人须知前附表"等复杂表格
- **YAML Front Matter**：存放结构化元数据（项目名称、采购编号、预算金额、时间节点等），渲染引擎据此生成封面和关键表格
- **法规版本管理**：法律法规引用条款集中管理，法规更新时只改一处，所有模板同步生效

### 4.3 与现有对比

| 维度 | 传统 Word 模板 | Markdown 方案 |
|------|---------------|--------------|
| 多个项目复用 | 复制粘贴 + 逐项修改 | 改 YAML 元数据一键生成 |
| 版本追溯 | 无从查起 | Git blame 精确到行 |
| 法规更新 | 逐个文件手工改 | 更新一个 include 文件全量生效 |
| 协作 | 邮件 + "最终版 v3 修订2" | PR review |
| 格式一致性 | 靠人的责任心 | 靠渲染引擎 |

## 五、给 rfp 模块的具体功能建议

结合本地 15 个文件的实战体感，优先做这些：

1. **模板市场**：预制货物/服务/工程三类模板，每类至少3个变体
2. **元数据驱动生成**：填一个表单（项目名/编号/预算/时间），自动渲染完整招标文件
3. **合规检查器**：见第三章第3.3节
4. **章节管理器**：可视化拖拽调整章节顺序，自动更新条款编号交叉引用
5. **差异对比**：两个版本招标文件的 diff（基于 Markdown 源码天然支持）
6. **导出双格式**：PDF（投标人阅读用）+ DOCX（用户二次编辑用）
